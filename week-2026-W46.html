Microsoft Patches 1,259 Flaws, Including Exploited Outlook Bug That May Expose NTLMv2 Hashes
thehackernews.com • Nov 11, 2026

Microsoft on Tuesday released patches for a total of 1,259 vulnerabilities spanning its software portfolio, the second consecutive month where the patch volume has exceeded 1,000 flaws. These cover 726 flaws in Windows, 174 in Office, 61 in Developer Tools, 59 in SQL Server, 53 in Developer Tools, and 27 in SharePoint Server. The patches also include 165 non-Microsoft-issued CVE identifiers. More than 500 flaws relate to elevation of privilege, followed by remote code execution and information disclosure bugs. With the latest round of fixes, Microsoft has addressed over 5,100 CVEs this year alone, according to Satnam Narang, senior staff research engineer at Tenable. Of these, a Moderate-severity security flaw in Microsoft Outlook (CVE-2026-124194, CVSS score: 6.5) has been flagged as actively exploited by Microsoft. "Product UI does not warn users of unsafe actions in Microsoft Office Outlook allows an unauthorized attacker to perform spoofing over a network," Microsoft said in an advisory. An unauthenticated attacker could send a specially crafted message file and persuade a target to open it in an affected version of Microsoft Outlook. This, in turn, could cause Outlook to connect to an attacker-controlled network location without displaying the usual external-content warning, potentially disclosing authentication information, such as an NTLMv2 hash, that could be used to impersonate the user. Microsoft emphasized that successful exploitation requires network connectivity and user interaction. The tech giant credited a researcher named Nono and Anthropic's Benoît Sevens (using Claude) with discovering and reporting the flaw. "Email is the easiest door into any company, and this flaw turns one opened file into a stolen identity," Jack Bicer, director of vulnerability research at Action1, said. "A captured hash can let an attacker sign in as the victim, read their data, and move to other systems they can reach." "The Moderate label undersells this one. Attackers are already exploiting it, it needs only one click on an email file, and it hits Outlook, which nearly every organization runs. A stolen hash can open doors far beyond the inbox." That said, Redmond has not attributed the activity to a particular threat actor or provided technical details on how the vulnerability is being exploited in the wild. The advisory also doesn't spell out whether the discovery came before or after attackers began exploiting the flaw. The development has prompted the U.S. U.S. Cybersecurity and Infrastructure Security Agency (CISA) to add the flaw to its Known Exploited Vulnerabilities (KEV) catalog, requiring federal agencies to apply the fix by November 24, 2026. Some other vulnerabilities of note include a number of remote code execution flaws impacting Windows Search (CVE-2026-116928), Lightweight Directory Access Protocol (CVE-2026-119958), Windows Schannel (CVE-2026-119952), Windows Virtual Filtering Platform (CVE-2026-95962), and Windows Xbox Live Networking Service (CVE-2026-112967), as well as a privilege escalation flaw in Azure OpenAI (CVE-2026-119990). "Most security teams haven't quite recovered from the last month of bumper-to-bumper critical vulnerabilities, emergency patches, and '2shell'-branded everything, and we're yet again at another Patch Tuesday," Jake Knott, head of threat intelligence at watchTowr, said. "Teams are really starting to feel the strain of working out 'what actually matters?' when there is fire after fire every day demanding immediate attention. Start with what you actually have exposed to the Internet, then what’s already being exploited in the wild, and only then everything else. Before going into panic mode, check whether you even use the vulnerable component, or meet the prerequisites for exploitation."

Support tip: Why Windows driver recommendations may vary between deployment rings
techcommunity.microsoft.com • Nov 13, 2026

By: Dorin Mardari – Sr Technical Support Engineer | Microsoft Intune Managing Windows driver updates across deployment rings might give results that seem inconsistent. You might expect the same update to behave the same way everywhere, but Windows Update evaluates updates separately for the devices in each ring. As a result, the update might appear under Recommended drivers in one ring and Other drivers in another, change classification over time, arrive at different times, or not appear at all even though the manufacturer's website lists it for your devices. In most cases, this behavior is expected. This article explains why it happens, what it means when you approve and deploy drivers, and how to tell expected behavior from a problem that needs Microsoft Support. For general information about driver update policies, approval modes, and the Recommended drivers and Other drivers lists, see: Where driver classifications come from Intune and Windows Autopatch don't decide whether a driver is recommended. - First, the publisher submits the driver. Many drivers are built by a component maker, such as a chipset, audio, or graphics vendor, but published to Windows Update by the original equipment manufacturer (OEM). The publisher decides which hardware the driver targets and whether it's marked as required. Only drivers marked as required can appear under Recommended drivers. - Windows Update then evaluates each device. Windows Update decides whether a driver applies, and how it ranks against other drivers that also apply. It bases this on the device's hardware IDs, currently installed drivers, the Windows version, and the publisher's targeting rules. - Finally, Intune shows the result for each policy. Each policy's driver list is built from the results for the devices assigned to it. Why the same driver can be listed differently in different rings A driver isn't classified once for your whole tenant. Instead, it's classified for each policy (ring), based on the devices in that policy. Two devices can get different results for the same driver depending on their model, already installed drivers, and Windows version, even within the same ring. When the devices are in different rings, each ring can show the driver differently. This is especially common for drivers that apply to several device models. One device can change how the whole ring shows a driver If a driver is recommended for at least one device in a policy, the policy shows it under Recommended drivers, even if it's only optional for the other devices. Example: - Ring A contains Device 1 and Device 2. The driver is recommended for Device 1 and optional for Device 2, so Ring A shows the driver under Recommended drivers. - Ring B contains only devices like Device 2, so Ring B shows the same driver under Other drivers. Both rings can be managed the same way and contain similar hardware, but they show different results because of one device. Changes can apply to only some devices Each driver published to Windows Update has a unique UpdateID. You can find it in the driver's Update Details in the Microsoft Update Catalog. The same driver name and version can be published several times, for example for different devices or components, or with different requirements. Each of these publications is a separate update with its own UpdateID. Windows Update can also deliver one update to several groups of devices, called flights. Flights are based on details such as the manufacturer, hardware, installed drivers, and Windows version. During a driver's rollout, Windows Update can change how the driver is ranked, for example from optional to recommended.

Hosted customers are also being recommended to follow N-able's previous guidance to upgrade Agents and Probes on N-central version 2026.4 HF1 and above, as the update introduces changes in how the Probe and Agent communicate. On-premises customers are being urged to upgrade Agents and Probes and ensure Legacy API access is disabled in the environment, if it has been previously turned on. "Our teams are actively assessing the new disclosures, developing additional remediation, and working to safely restore affected functionality," N-able said. "Protecting our partners and their customers remains our highest priority, and we will continue to take precautionary action where necessary." The development comes as independent security researcher Sean Bales disclosed two new sets of flaws called 4EverAble2Shell and Agent2Shell that work against the latest version of N-central and can allow attackers to execute arbitrary code as root and gain SYSTEM-level access to Windows systems under specific conditions. In an exploit chain detailed by the threat intelligence company, threat actors have been observed attempting to download and execute a shell script ("jup.sh") from an attacker-controlled server at "157.20.241[.]16," while sending back diagnostic information and command output to the server.
