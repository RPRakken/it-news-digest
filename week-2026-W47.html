Hybrid intelligence on the Web: Introducing Aion Instruct and Prompt API in Microsoft Edge Rapidly evolving AI capabilities are redefining what sites can do for users on the web. With on-device AI in Microsoft Edge, sites can use task-specific and small language models for capabilities such as writing assistance, summarization, language detection, translation, and speech recognition. Through the Prompt API, they can also use a small language model for more general-purpose intelligence. Together, these capabilities provide a foundation for hybrid intelligence on the web: developers can leverage on-device AI models when they are available in the browser and well-suited, and switch to a configured cloud provider to extend device coverage or access more powerful inference when needed. To make on-device inference more broadly available, we’re introducing three updates today: - General availability of Aion Instruct as an open-weights model on Hugging Face, and as Microsoft Edge’s built-in small language model. - An origin trial for the Prompt API, so you can use the Prompt API and Aion Instruct on your live site today. - A developer preview of an experimental Decisions API, which gets you fast, structured answers about text. These announcements build on our earlier developer preview of Aion-1.0-Instruct. Since then, we’ve heard from early adopters, incorporated your feedback, and refined the model’s training to improve quality and performance for on-device AI needs on the web. Aion Instruct is now generally available in Edge Aion Instruct is available today as an open-weights model on Hugging Face and is coming to Windows later this year, laying the foundation for richer on-device AI experiences across Windows and Copilot+ PCs. In Microsoft Edge, Aion now replaces Phi-4-mini as the browser’s built-in small language model. At 2.3B parameters, Aion is smaller, faster, and available on many more devices than Phi, while delivering comparable quality for common web tasks such as text synthesis and generation, summarization, instruction following, and structured outputs. Edge downloads Aion Instruct only when a site or feature first needs it, and only on devices that can run it well. Users stay in control and can turn off on-device AI in Edge settings, which removes the model and stops future downloads. Test the Prompt API on your live site Until now, the Prompt API has been available as a developer preview only in Edge Canary and Dev channels. Now, with the Prompt API origin trial, you can call the API from your live site in Microsoft Edge and test it with a much broader audience. The origin trial lets you bring on-device AI features to your site, evaluate them under real-world conditions, and refine your implementation based on actual usage. Along the way, please share feedback on the API’s design, the model’s performance, and any interoperability challenges you encounter across different browsers and models. This will help inform discussions with other browser vendors and the web community as the Prompt API is considered for standardization. To get started, register for the Prompt API Origin Trial, read the developer documentation, try out the playground sample, and engage with us on the GitHub discussion about the API. Developer preview of the Decisions API We’re also exploring new uses for on-device AI with an early implementation of the experimental Decisions API, powered by Aion Instruct. It is available as a developer preview in Edge Canary and Dev channels for prototyping. Expect both the API and its implementation to change as we learn from developer feedback. The Decisions API enables sites to ask yes/no, multiple-choice, or scoring questions about text input and get back probabilities and a confidence value, computed in a single pass without any text generation.

Enterprise Deployment of Governed Agents on Windows
blogs.windows.com • Nov 17, 2026

As AI agents become more capable, they promise substantial productivity gains across enterprise workflows. At the same time, they can collapse familiar execution boundaries and introduce new risk paths—from agent to human, agent to agent, agent to tools, and agent to applications. That tension can leave organizations facing an unacceptable choice: give agents broad access and hope nothing goes wrong or block them and forgo the value they can deliver. Traditional application controls remain essential, but they were not designed to express the full context of an agent’s execution across tools, child processes, files, network endpoints, and long-running sessions. Running agents safely at enterprise scale requires three foundational operating-system primitives: identity, containment, and manageability. Identity When an agent operates on a user’s behalf, its actions must be distinguishable from the user’s own activity. Agent identity creates this separation, making agent activity identifiable so organizations can apply appropriate security, access, and governance controls. Windows and Microsoft Entra are working together to support agent identity across local and cloud interactions. Microsoft Entra Agent ID provides the identity foundation for governing agent access to resources, while Windows provides the local isolation boundaries that help separate agent activity from the user. Containment Containment limits agent behavior to only the resources required for the assigned task. Microsoft Execution Containers (MXC) provide platform-enforced boundaries for this control. For example, if an agent is asked to build a website, it should access the project folder only, not personal files or unrelated sensitive data. MXC enforces those boundaries through Windows platform controls, not just policy guidance. Different agent patterns require different containment strength. A coding assistant may need lightweight process isolation, while a fully autonomous agent may require stronger isolation, including separate Windows sessions. Windows provides this containment spectrum so isolation can be matched to workload risk. Management Organizations need centralized visibility and control over agent deployment, access, and policy enforcement. Windows connects agent operations to the Microsoft security and management ecosystem. - Microsoft Intune and other MDM solutions define and manage agent containment, configuration and compliance policy. - Microsoft Entra governs identity, authentication, and access. - Agent 365, Microsoft Defender, and Microsoft Purview extend observability, security, and management into agent activity workflows. Why identity is foundational Identity is the control anchor across all three domains. It establishes which agent is acting, enables the correct containment model, and carries policy context into interactions across devices, applications, and cloud services. The target state is consistent governance across endpoint and cloud, rather than fragmented controls. Where Microsoft Execution Containers (MXC) fits in an enterprise agent-security strategy Microsoft Execution Containers (MXC) should be treated as a key layer in a defense-in-depth architecture, as it connects with identity, endpoint, data, or application controls. Its distinctive role is to govern execution: which resources a local agent process can reach, and how strongly the workload is isolated. This closes the gap between granting a user access and constraining what an agent running on that user’s behalf can do. The strongest design separates responsibilities across the control plane: - Identity and access with Microsoft Entra Agent ID: Agent identity helps distinguish agent activity from a user’s own activity so organizations can apply appropriate access, security, and governance controls.

Government sectors in Asia and Africa have been targeted by an active cyber intrusion campaign that delivers to previously undocumented backdoors that leverage legitimate services like Microsoft SharePoint and GitHub for command‑and‑control (C2). The activity has been codenamed Operation ShadowCloud by Kaspersky. The Russian cybersecurity company said it identified the campaign in early 2026. "The threat actor behind it is abusing the legitimate MeshAgent utility to drop two brand-new backdoors," Kaspersky researchers Saurabh Sharma and Noushin Shabab said in a two-part analysis. "These implants hide their command‑and‑control (C2) traffic behind cloud services Microsoft SharePoint, GitHub, and Ably, allowing the implants to blend in with normal traffic, effectively evading network-based detections." The modular backdoors, dubbed GraphDoor and GitDoor for their choice of the cloud platform used for C2, enable the download of additional plugins on demand and the execution of shellcode directly in memory to extend their functionality. Traffic between infected systems and the C2 servers is proxied by deploying a modified Erfrp client and Ably messaging service-based plugins. The starting point of the attack has been traced back to a MeshCentral Agent, a legitimate remote access tool that's used for remote desktop control, command‑line access, and file management. The attack is said to have targeted an unspecified Taiwanese organization. The exact method by which the utility is installed on the host remains unknown. However, signs point to the "reuse of a prior infection already present on the network," Kaspersky added. The MeshCentral Agent is configured to contact a hard-coded C2 server ("wss://27.102.66[.]162:443/agent.ashx") and then fetch three payloads staged on the endpoint - - A legitimate binary used for DLL sideloading (start.exe, pythonw.exe, and zoomit.exe) - A rogue loader DLL used to unpack and execute the next-stage malware (jli.dll, SbieDll.dll, python39.dll, WINMM.dll, and libcef.dll) - An encrypted file containing the core payload At least two different DLL loaders have been identified to date, each employing its own method to decode and launch the encrypted backdoor payload by injecting it into the current process's memory. "Loader (Type 1) employs a hybrid scheme: first running the data through an RC4 stream cipher and then applying an XOR mask, while Loader (Type 2) simplifies the process by using a straight XOR operation alone," Kaspersky noted. The end goal is to deploy backdoors like GitDoor and GraphDoor, which employ a number of encryption and obfuscation techniques like control flow flattening and nested helper functions to complicate analysis efforts and make it harder to trace genuine execution flow. GitDoor, as the name implies, uses GitHub for C2. It relies on two distinct repositories for receiving command payloads ("/repos/LatonyCharnleyaW/Havo") and uploading the results of the execution ("/repos/LatonyCharnleyaW/Trix"). While the Havo repository is public, the Trix repository is private. The creation date of these repositories suggests that preparations for the campaign have been underway since at least the end of 2024.
