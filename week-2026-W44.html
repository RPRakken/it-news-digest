Edge is faster on Windows with Accelerated App Launches
blogs.windows.com • Oct 29, 2026

Edge is faster on Windows with Accelerated App Launches We’re excited to announce that Edge is the first browser to support accelerated app launches on Windows, delivering a faster and more consistent browser launch experience. With accelerated app launch, most Windows users will see a 15% launch speed improvement, with wins of up to 33% under heavy multitasking!1 That means you can start browsing faster. This has already rolled out starting with Microsoft Edge version 150 and later and is supported on Windows 11, versions 25H2, 26H2, 26H1 with the October 2026 non-security update (KB5127936) or later. How does this work? The Edge and Windows team partnered to bring this new Windows accelerated app launch capability to Edge users quickly. Edge, like many modern applications on Windows, is often already running. A visible Edge window might already be open, or Edge might already be running in the background through features such as Startup Boost. Without accelerated app launches on Windows, when you click on a link or start Edge from the taskbar, Windows must first determine if Edge is already running. To do that, Windows starts an intermediary process that looks for the already-running browser and, if one is found, forwards the request. On a PC that just started, you might barely notice. But in real multi-tasking scenarios, the extra work of having to look for an existing Edge process could make Edge feel slow. Now, with accelerated app launches on Windows, when an Edge process starts, it sends a registration request to Windows. Windows checks and accepts the request. Later, when Edge is launched again, Windows can use the accelerated-launch registration to notify the already running Edge process directly. Accelerated app launches are supported by the Start menu and the Taskbar and opening supported links that open in Edge by default. For developers who are interested in supporting accelerated launches in their own Windows apps, see Register your application for accelerated app launches. Making Edge work great on Windows Accelerated app launches is part of our work to make Edge work great on Windows and we’ll continue innovating in this area. We’re working with Windows on adding other ways to utilize this feature, such as when opening PDF files. We’re also contributing this work to Chromium, the open-source project which Edge is based on, so other Chromium-based browsers can benefit from accelerated launches on Windows in the future. 1 Compared to launching Microsoft Edge without accelerated app launch in Windows, when Edge is already running. Requires Windows 11 (25H2, 26H1 or 26H2) with KB5127936 or later and Edge 150+.

Microsoft finally fixes VPN issues caused by September updates
bleepingcomputer.com • Oct 30, 2026

Microsoft has resolved Always On VPN connection failures triggered after installing the September 2026 Windows 11 security updates. The Always On VPN remote access solution runs in the background and establishes secure tunnels back to the user's corporate network when their devices connect to the Internet. It has replaced the legacy DirectAccess technology and supports domain-joined, non-domain-joined, and Microsoft Entra ID–joined devices running Windows 10, Windows 11, and Windows Server. Microsoft has previously mistakenly flagged this known issue as fixed in the October 2026 Windows 11 cumulative updates. The company first acknowledged it in a service alert sent to IT administrators in late September, saying the Always On VPN failures were triggered on Windows 11 systems by the September 2026 security updates when using automatic protocol selection with IKEv2 and SSTP. On Wednesday, Microsoft confirmed that this issue has finally been fixed for users who installed this month's KB5127936 preview update. "This update fixes an issue that affects Always On VPN connections after installing September security update," it said. "When automatic protocol selection or protocol fallback was configured, affected VPN connections could remain stuck in a Connecting state or fail to connect after an initial connection attempt failed. In some cases, subsequent connection attempts could display the error, 'The specified port is already in use.'" Workaround also available Microsoft also provides a temporary fix for users who don't want to install the preview update and would rather wait for next month's Patch Tuesday cumulative updates. This requires admins to choose one of two tunneling protocols to prevent Always On VPN failures on affected devices. "IT administrators can mitigate this issue by changing the Always On VPN profile from automatic protocol selection to a single protocol, either SSTP only or IKEv2 only, depending on their environment and configuration," Microsoft said. "Organizations should select the protocol based on their environment, security, and deployment requirements." The October 2026 preview update also fixes a known issue preventing non-admin users from connecting to devices via Remote Desktop when the "Administrator protection" security feature is enabled after installing the September 2026 Windows 11 non-security preview update (or Windows updates released since then). Azure Cloud HSM Hardware Audit Logging: Verifiable audit trails for security and compliance
azure.microsoft.com • Oct 29, 2026

Organizations running regulated and security-sensitive workloads need trusted evidence of which authenticated users performed management operations on their hardware security modules (HSMs), what actions they took, and when. Today, we are announcing Hardware Audit Logging for Azure Cloud HSM, which collects audit records generated by the HSM itself for supported management operations. Security, compliance, and operations teams can use this hardware-originated evidence for monitoring, compliance reporting, and forensic investigations. Why hardware-generated audit evidence matters HSMs protect some of an organization’s most sensitive cryptographic assets. The security of those assets depends not only on how keys are generated and protected, but also on how the HSM is configured and administered over time. Authentication events, user changes, policy updates, backup operations, and key lifecycle activity can all be important when teams investigate an incident, validate operational controls, or prepare evidence for an audit. Traditional platform and application logs remain valuable, but regulated organizations often want evidence that originates as close as possible to the protected cryptographic boundary. By sourcing audit information directly from the HSM, Azure Cloud HSM provides records tied to the device performing the protected operations. This gives customers an additional layer of evidence for understanding administrative activity and validating the records incorporated into their monitoring and compliance processes. Monitor HSM management operations with hardware-generated audit logs Hardware Audit Logging captures a broad range of HSM management activities, including: - User authentication and session events. - User and administrator management. - Policy and configuration changes. - Key lifecycle operations. - Backup and restore activities. Together, these events help organizations build a more complete view of how the HSM is being operated. Security teams can examine authentication and administrative activity, compliance teams can use the records as evidence for control assessments, and operations teams can investigate configuration or lifecycle changes that may affect a protected workload. Independent, end-to-end audit verification Customers can access human-readable audit records, the corresponding HSM-signed binary audit data, signatures, and HSM certificates needed to independently verify the authenticity and integrity of signed audit batches. This customer-controlled verification path helps connect the records used in monitoring and reporting back to the signed evidence produced by the HSM. This approach is important because auditability is not only about collecting readable events. It is also about establishing confidence in where the records came from and whether the signed audit batches remain intact. Maintain consistent audit coverage for supported management activity Audit logging is enabled as an immutable HSM partition policy. This design helps maintain consistent coverage of supported management activity and reduces the risk that logging could be disabled as part of routine HSM administration. For organizations that separate cryptographic administration, security monitoring, and compliance responsibilities, continuous hardware-originated logging can support clearer oversight across those functions. The capability is designed to complement an organization’s existing governance model. Customers remain responsible for configuring access to their monitoring environment, defining retention requirements, establishing alerting and review processes, and determining how audit evidence should be used within their control framework.

Scale reservoir uncertainty analysis with agile reservoir modeling
azure.microsoft.com • Oct 26, 2026

Turn subsurface uncertainty into decision-ready insight Drilling campaigns are among the most expensive and operationally complex activities in the energy industry. Rigs, crews, equipment, and logistics are scheduled months in advance, leaving little room for delay. Every hour of downtime can carry significant costs. Geoscientists and engineers rely on reservoir models to understand the subsurface and guide drilling decisions, often under intense time pressure. Yet the current modeling infrastructure that many companies rely on for these critical decisions was designed for smaller datasets, simpler workflows, and siloed operations. As subsurface data grows in scale and complexity, teams need a faster, more connected way to transform uncertainty into actionable decisions. Now generally available, agile reservoir modeling (ARM) from SLB, integrated with Azure Data Manager for Energy (ADME), is co-engineered for cloud scale to close that gap. The combined solution connects ensemble-centric reservoir modeling and simulation with a governed data foundation, elastic Azure high-performance computing, and scalable storage designed for the throughput and concurrency of large ensemble studies. Scale ensemble modeling with ARM on Azure A single reservoir model represents one plausible interpretation of the subsurface. Ensemble modeling evaluates hundreds of model realizations together, giving asset teams a broader view of potential outcomes and a stronger basis for understanding uncertainty and risk. The industry has long recognized the value of ensemble modeling for risk-aware decision-making, but adoption has been constrained by infrastructure and software designed for smaller, sequential studies. Moving from a limited model set to hundreds of realizations multiplies the compute, storage, data movement, and results that must be managed. ARM addresses this barrier by distributing realization generation and simulation across elastic Azure high-performance computing, while scalable storage provides the capacity, throughput, and parallel access required by ensembles of different sizes. Connect reservoir workflows to a governed data foundation Building and updating reservoir models draws on many systems: seismic, wellbore, interpretation, and simulation data, plus the applications and compute that process them. When these pieces are fragmented, customers must connect and orchestrate them on their own, and large-scale simulation becomes a disconnected, one-off exercise. SLB and Microsoft combined their respective technologies, ARM engineered by SLB and ADME engineered by Microsoft, to remove that burden. Rather than a set of loosely connected tools, customers get one integrated workflow in which each component has a clear role: - Azure Data Manager for Energy is the governed data foundation. OSDU® Technical Standard-aligned services and OSDU Domain Data Management Services (DDMS) manage seismic, wellbore, interpretation, and simulation data. - Petrel™ subsurface software is where engineers define interpretation and uncertainty workflows, connected directly to data in ADME. - Agile reservoir modeling is the ensemble workflow engine. It orchestrates the generation of reservoir realizations and simulation runs and supports discovery and analysis at enterprise scale. As a result, teams build ensembles from trusted corporate data and publish results back for discovery and reuse, which reduces data movement and improves collaboration across asset teams. Put ensemble modeling into practice with a connected workflow Beyond integration and scale, ARM distinguishes itself by orchestrating all stages of an ensemble study across modeling, simulation, data management, and analysis.

Establish a macOS security baseline with mSCP and Microsoft Intune custom compliance
techcommunity.microsoft.com • Oct 28, 2026

By: Iris Yuning Ye, Product Manager | Microsoft Intune Organizations that manage Mac devices need a reliable way to evaluate their security posture against a recognized baseline. Microsoft Intune custom compliance provides the device compliance evaluation policy, and the National Institute of Standards and Technology’s (NIST) macOS Security Compliance Project (mSCP) provides macOS security rules and checks mapped to compliance requirements. Earlier this year we released Intune custom compliance for macOS devices. The feature uses a discovery script and JSON file to define compliance settings. With the mSCP command-line tool, you can select and tailor a security baseline, generate a macOS discovery script, and pair the discovered identifiers with an Intune rules JSON file. Intune then evaluates each device against the chosen baseline and uses the result in compliance reporting and Conditional Access decisions. In this blog, we’re introducing a JSON conversion script (mscp_to_intune_json_conversion.sh). The script converts the mSCP’s generated vendor manifest into the JSON format required for Intune custom compliance. &nbsp; Figure 1: Prerequisite Before you begin, set up the mSCP locally by following the NIST guidance: Getting started with the macOS Security Compliance Project. Create a security baseline Next, we’ll establish and configure the security baseline on the device. Select your security baseline: Choose a security baseline your organization intends to evaluate devices against by looking through frameworks supported by mSCP (for the example in this blog we’ll use CIS Level 1) Configure your baseline: When creating the baseline for the first time, you'll follow a guided process to specify the name of the custom baseline, your name and organization, choose what specific rules to include or exclude. Once the customization process is completed, a new baseline file containing all the rules you specified is generated under the custom/baselines/ directory as a YAML file. ./mscp.py baseline –k cis_lvl1 –t Note: The command uses the following flags: -k Specifies the keyword. In this example, we're using cis_lvl1. -t Enables tailoring, allowing you to select specific rules to include and define organization-specific values. Figure 2: Sample results after running the baseline keyword and tailoring command.Figure 3: Sample of tailoring each security baseline rule to your organization's need. Once the baseline YAML file is generated, run the command below to generate mSCP documents. These files will be saved into a build/[your specified project name] directory. ./mscp.py guidance –s –M [yaml file location] &nbsp; The yaml file location should be the relative location on top of your mSCP folder. Note: The command uses the following flags: -s Generates the compliance script. -M Generates the JSON vendor manifest file. Figure 4: Command line shows mSCP document generation complete. Once the JSON Vendor Manifest and compliance script are successfully generated, we highly recommend running a test check to verify that all rules and values are defined as expected. Note: If you're using the container method, exit the container to proceed to run the check. (Exit container: NIST macOS Security Getting Started) &nbsp; The key is to locate where you build folder is and where the .sh file was saved in: sudo ./[base folder]/cis_lvl1_macos_27.0/cis_lvl1_macos_27.0_compliance.sh --check &nbsp; Figure 5: Run check to confirm security baseline rule was set as expected. Create mobileconfig file Create a mobileconfig file by creating a plain text file, then copy and paste the example in GitHub into it. &nbsp; Figure 6: Sample mobileconfig file. Configure the .mobileconfig profile Update the PayloadType key to match the audit file name. This ensures the compliance script uses the correct managed arguments when running.Example: In our demo, the value is updated to:org.intune_compliance_lv1_macOS_26.0.audit Customize the following keys based on your organization's requirements and preferences: PayloadDescription PayloadOrganization PayloadDisplayName Test the .mobileconfig profile To verify the configuration, install the .mobileconfig profile locally on a test MacOS device. Open System Settings &gt; General &gt; Device Management. Select the + button to add a configuration profile. Navigate to the saved .mobileconfig file, select it, and click Open. Follow the prompts to Continue and Install the profile. Note: Administrator privileges are required to install the device profile. &nbsp; Validating the Results:Once the profile is installed, run the generated compliance script. If the script runs successfully and outputs JSON, the managed arguments are correctly set. Run the generated compliance script with no arguments specified to make sure it uses the managed arguments from the installed mobileconfig file. &nbsp; sudo ./[base folder]/cis_lvl1_macos_27.0/cis_lvl1_macos_27.0_compliance.sh &nbsp; Figure 7: Sample result from running the script locally. Once testing is complete, remove the test profile for your local Mac. It’s critical to ensure all testing profiles are removed from target devices before deploying from Intune to avoid conflicts. You can deploy the custom mobileconfig profile for the managed arguments using Intune to the desired set of macOS devices. Important: Deploy the .mobileconfig file to target devices before deploying the custom compliance policy. Otherwise, the custom compliance policy may not run correctly. Use JSON conversion script Next, use the mscp_to_intune_json_conversion.sh script from GitHub to convert the mSCP JSON Vendor Manifest file into the specific JSON format required for Intune’s custom compliance policy. The command line is comprised of three parts: Locate where you saved the conversion script. Specify the JSON file from security baseline you intend to convert from. Specify the name of the custom compliance JSON file you intend to convert to. ~/ mscp_to_intune_json_conversion.sh [base folder]/cis_lvl1_macos_27.0/cis_lvl1_macos_27.0_compliance.json &gt; intune_custom_compliance.json &nbsp; Figure 8: Using JSON conversion script to convert mSCP generated rule file into Intune custom compliance policy compatible JSON file. You can now upload the compliance script built by the mSCP that can be found in the build directory as your Discovery Script within Intune’s custom compliance policy. &nbsp;You can also upload the converted JSON file as the JSON for custom settings.Devices with the mobileconfig profile installed will run the compliance script using the managed arguments and output the JSON required for the custom discovery script. Keep in mind Start with a small pilot group and a focused baseline of your choice. Validate every identifier, returned data type, and expected value before broad deployment. Deploy mobileconfig file and make sure the file is already successfully deployed on target devices before custom compliance policy. Review the per-setting results in the Intune admin center &gt; Reports &gt; Device compliance -&gt; Noncompliant devices and settings. Make sure the JSON file generated is aligned with other discovery scripts’ output to avoid misalignment errors. The recommended first step is to pilot one baseline on a small Mac device group, document the source version and rule mapping, and expand only after the discovery script output and Intune results have been validated. Conclusion The steps and scripts provided simplifies the flow to connect the mSCP with Intune’s custom compliance feature. By leveraging mSCP, organizations can efficiently translate recognized macOS security guidance into actionable, measurable compliance signals. While Intune provides the mechanism to capture identifiers and current device values, the rules JSON define the precise evaluation criteria. Together, these tools create a transparent, automated path from a high-level security baseline to detailed, device-level compliance reporting.
